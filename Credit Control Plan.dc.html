Naafco Business Intelligence · Pre-implementation review

Credit Control module

Inspection of the existing frontend and warehouse, the components the module should reuse, and what has to be built. Nothing is coded in the application yet — the mockup beside this document is a design artefact, not a patch.

Source read: MdimtiazHossain/Naafco_Business_Intelligence@main · 2026-08-29

One finding to settle before anything is built

This platform had a receivables surface and deliberately removed it. Migration 0020_remove_receivables_and_warehouse dropped fact_outstanding, fact_collection, vw_customer_outstanding and vw_outstanding_aging because no source extract was ever produced; CLAUDE.md now states "there is no receivables reporting, no aging, no overdue", the AI prompt refuses those questions, and the HIGH_OVERDUE alert was deleted.

Credit Control reinstates that capability with a source that does exist. That is a policy reversal, not just a new page: ai/prompts.py, ai/tools.py, ai/schemas.py and CLAUDE.md must be updated in the same change, or the assistant will keep telling users the company does not track overdue while the sidebar shows a page that does. The upside is that 0020's downgrade() is the schema blueprint — days_overdue, aging_bucket and their indexes already existed in this shape.

3 · Where it goes

Nav position: MAIN_NAV in layouts/AppLayout.tsx, immediately after Customers and before Map — the customer-money entry belongs beside the customer entry, and the operational reports stay grouped above the data-admin block.

Route: /credit-control, lazily loaded and wrapped in <Guarded section="credit_control"> like every other report.

Permission: a new SectionKey 'credit_control' in types/api.ts and in the backend section registry, seeded for MANAGEMENT and FINANCE roles only. Credit exposure is more sensitive than sales volume and should not ride on the customers grant.

4 · Data model recommendation

Migration 0026_credit_control, following the platform's own conventions: staging keeps the source shape as TEXT, the fact holds typed values, nothing is truncated, new columns carry server defaults.

stg_credit_invoice          every business column TEXT + StagingMixin
                            (staging_id, source_file, source_row_number,
                             batch_id, loaded_at, status, error_code)

fact_credit_invoice
  ── source columns ─────────────────────────────────────────────
  company_code       str(10)   indexed
  invoice_no         str(32)   indexed, unique with company_code
  plant_code         str(10)   indexed   → dim_plant
  customer_code      str(20)   indexed   → dim_customer (name lives there)
  invoice_date_id    int       indexed   → dim_date
  credit_days        int                 CHECK IN (30,45,90,150,180,190,250)
  invoice_value      numeric(18,2)       CHECK >= 0
  return_amount      numeric(18,2)       CHECK >= 0
  payment_amount     numeric(18,2)       CHECK >= 0
  discount_amount    numeric(18,2)       CHECK >= 0
  adjustment_amount  numeric(18,2)       CHECK >= 0
  payment_mode       str(8)              CHECK IN ('CASH','CREDIT')
  last_payment_date_id  int   nullable   → dim_date
  clearing_date_id      int   nullable   → dim_date
  clearing_document  str(32)  nullable   indexed (searchable)
  ── derived, written by the ETL, never by a user ───────────────
  net_invoice_amount numeric(18,2)   invoice_value − return_amount
  balance_amount     numeric(18,2)   net − payment − discount − adjustment
  due_date_id        int   indexed   invoice_date + credit_days
  days_overdue       int   indexed   max(as_on − due_date, 0)
  aging_bucket       str(16) indexed  NOT_YET_DUE | 1-30 | 31-60 | 61-90
                                      | 91-120 | 121-180 | 181-365 | 365+
  credit_status      str(16) indexed  NOT_YET_DUE | OVER_DUE | CLEARED
  data_quality_flag  str(32) nullable BALANCE_NEGATIVE | DUE_DATE_MISMATCH
                                      | BALANCE_MISMATCH
  source_system, source_file, batch_id, loaded_at

views   vw_credit_invoice_detail    row-level, joined to customer/plant names
        vw_customer_credit_exposure per-customer totals, oldest due, last payment
        vw_credit_aging             bucket × count × outstanding
  • Status and aging are computed in one place — a single SQL expression used by the fact refresh and by every view, so no endpoint can define "overdue" differently.
  • Balance is not floored. An over-adjusted row keeps its negative figure and gets data_quality_flag = BALANCE_NEGATIVE; it counts as Cleared for status, is excluded from aging, and is listed on the Data Quality page. Source data is never overwritten.
  • Due Date is recomputed, not trusted. If the file carries one and it disagrees with invoice_date + credit_days, the derived value wins and the row is flagged.
  • Credit days: a CHECK against the seven values, not a new master table, unless configurable terms per customer are actually wanted — say so and it becomes dim_credit_term.
  • No duplicate customers. Customer View groups dim_customer rows; the module creates no customer record and displays Customer Name with the code as secondary text.

5 · API requirements

Endpoint
Returns
GET /api/reports/credit-control
One page bundle like /api/dashboard: six KPIs, aging buckets, status split, top overdue customers, outstanding trend, resolved period, result notes. All aggregated in SQL.
GET …/credit-control/invoices
Server-paged rows + total, total_pages. Params: filters, search, sort_by, sort_dir, page, page_size, as_on_date.
GET …/credit-control/customers
Customer View rows, server-paged and server-sorted on the same filter set.
GET …/credit-control/invoices/{no}
One invoice for the detail panel, including the flag and whatever payment events exist.
POST /api/export
Existing endpoint, unchanged — ExportButtons already sends report name, period, filters and rows.
  • as_on_date is a first-class parameter: overdue is a function of a date, and "what did we look like at month end" is a question the finance team will ask. Defaults to today.
  • Due-soon horizon is a config setting (app/config.py, like the stock expiry horizon) with a per-request override — the Stock page's expiring_within_days selector is the pattern.
  • Credit Days, Payment Mode and Status are STATIC_OPTIONS in FilterContext — fixed sets, so no options request. Customer and Plant use the existing /api/master-data/options/{level}, which already truncates and permission-scopes.
  • Every endpoint applies the caller's data scope, the same way the sales and stock reports do.

7 · Implementation plan

Step 1 · Decide the reversal

Confirm receivables reporting returns. Update CLAUDE.md, README, ai/prompts.py, ai/schemas.py, ai/tools.py. No UI work until this is agreed.

Step 2 · Warehouse

Migration 0026: staging, fact, indexes, three views. One shared status/aging SQL expression. Tests for the calculation rules and each data-quality flag.

Step 3 · ETL

A DatasetSpec for Credit Invoice in etl/datasets.py with column aliases, validation rules and the derivations. The upload centre and the batch/rejection machinery then work unchanged.

Step 4 · API + permissions

Four endpoints, the credit_control section, role seeding, config setting for the due-soon horizon.

Step 5 · Frontend

Nav item, route, CREDIT_FILTERS, the page assembled from existing components, the detail panel, creditService, en + bn translations, the two additive changes to Charts.tsx and format.ts.

Step 6 · Assistant, alerts, dashboard

Reinstate the outstanding tools and the HIGH_OVERDUE alert; optionally one Overdue card on the executive dashboard.

Step 7 · Verification

Backend tests for the rules; frontend tests beside stockFilters.test.tsx for the filter set, the status badges and the drill-down; a volume test at the real row count before release.

8 · Decisions I need from you

  1. Aging buckets. The platform's existing convention is six (CURRENT · 1-30 · 31-60 · 61-90 · 91-180 · 180+) and AGING_COLORS is built for them. Your brief asks for eight. The mockup uses your eight and adds two colours — confirm, or keep the six the rest of the system knows.
  2. Date format. You picked 2026-08-15; the app's formatDate renders 15 Aug 2026 everywhere else. The mockup shows ISO. Change it app-wide, or accept Credit Control looking different?
  3. Credit exposure. No credit limit exists in the Customer Master, so exposure is shown as a share of portfolio outstanding. If you want limit-vs-used exposure, the limit has to be added to the master first.
  4. Negative adjustments. Are credit notes ever posted as a negative Adjustment Amount? If yes the >= 0 check has to go and only BALANCE_NEGATIVE stays as a flag.
  5. Payment history. Does the source hold individual payment transactions, or only the aggregate plus Last Payment Date? The timeline shows one payment event until told otherwise.
  6. Row count. Rough invoice volume, so pagination and index choices are sized against reality rather than a guess.

No application code has been changed. Say the word and I will start at step 1.
